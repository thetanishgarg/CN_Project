Phase 1

Task A: one private LAN

Claim. All four Macs share one subnet and reach each other at layer 3.

How it is proved. Each test script pings the other three Macs and prints its own interface facts.

Layer 2 cross-check: in the 22 November packet capture the TLS traffic is exchanged with Ethernet address 7e:45:9b:f9:71:19, the address Mac 2 prints for itself above on 23 November. The edge on the wire really is Mac 2.

Phase 1

Task B: private DNS

Claim. Our own server answers for team1.test, refuses unknown names in the zone, and forwards everything else.

How it is proved. A client’s checks, the decoded DNS packet, and the server’s own query log.

Phase 1

Task C: the two backends

Claim. One program, started twice, gives two distinguishable services.

How it is proved. Raw responses from each process, including the 404 path and the listening sockets.

Phase 1

Task D: load balancing

Claim. The edge spreads requests over both backends by round robin.

How it is proved. The X-Backend header of consecutive requests through the edge, in every recorded run that reached it.

Likely reasons for the uneven runs: nginx keeps one rotation for all clients, so another Mac’s requests fall between ours (the 11:58:02 runs on Mac 2 and Mac 4 carry the same time stamp), and a backend that just failed is skipped for 10 seconds. The nginx logs that would settle it were not saved. The last three runs of the day alternate strictly.

Task E: HTTPS with our own CA

Claim. The edge presents a valid certificate from Team1 Local CA and clients accept it without -k.

How it is proved. The certificate was taken out of the captured packets and verified again here, including cases that must fail.

Phase 1

Task F: HTTP caching

Claim. A client can reuse a response for 60 seconds, then revalidate it for free, whichever backend answers.

How it is proved. Conditional requests through the edge, the same ETag on both backends, and what Chrome itself did.

Step in real ChromeHTTP/1.1 reply (as behind the edge)HTTP/1.0 reply (backend.py directly)
1. First visitHTTP 200, 223 bytesHTTP 200, 223 bytes
2. Visit again within 60 sserved from Chrome’s disk cache, server not contactedserved from Chrome’s disk cache, server not contacted
3. Normal reloadHTTP 304, 181 bytes, sent If-None-MatchHTTP 200, 223 bytes
4. Hard reload (cache bypassed)HTTP 200, 223 bytesHTTP 200, 223 bytes

Chrome/158.0.8127.38, recorded through the DevTools protocol on one Mac over plain HTTP. Files: chrome-cache-http1.1.json, chrome-cache-http1.0.json.

Finding: Chrome did not revalidate an HTTP/1.0 response, and Python’s server speaks HTTP/1.0. Behind nginx the browser receives HTTP/2, so revalidation works. To show 304 in a browser, open the site through the edge, not the backend port.

Phase 2

Extension A: backup DNS

Claim. Mac 4 can answer for the zone when Mac 1 cannot.

How it is proved. Both servers checked on the LAN, the backup’s own log, and a one-Mac run where the primary is killed.

Still to record. A raw dig on the LAN with Mac 1 stopped. An earlier hand-made output was removed from the repository because it could not be traced to a recording. Run capture-lan.sh failover.

Phase 2

Extension B: short TTL

Claim. A 30-second TTL bounds how long clients keep an old answer.

How it is proved. The TTL in the captured packet, the TTL check on both servers, and a client that kept the old address for 29 seconds.

Client side: in the cutover below, the DNS server changed at 12:12:40 and the client’s cache changed at 12:13:09. Between the two, dig and the application disagreed, exactly as a cache should behave.

Note. An earlier hand-made TTL output was removed from the repository for the same reason; the cutover recording above replaces it.

Phase 2

Extension C: backend isolation

Claim. Only the edges may connect to a backend port.

How it is proved. In two runs started 37 seconds apart: the edge reaches both backends, a client is blocked from Backend A, and the same client still gets answers from A through the edge. A dead backend could not produce that combination.

Still to record. The live rule listing (capture-lan.sh firewall), and the same proof for Backend B on Mac 4.

Phase 2

Extension D: backend failover

Claim. A backend can die and return without a client seeing an error.

How it is proved. 20 requests through the edge while Backend A was stopped and restarted, 23 November 12:08:58 to 12:09:53.

Phase 2

Extension E: edge cutover by DNS

Claim. Traffic moves from the primary to the standby edge by changing one DNS record, with no failed request.

How it is proved. A client sampled the DNS answer, its own cache and the edge that replied about every 2.2 seconds.

Switching back exposed a real weakness. The record returned to Mac 2 at 12:14:31, the client followed at 12:15:04, and every request then failed. A test at 12:20 found the primary edge not serving. Lesson: check the target edge before moving traffic to it. The next section covers that outage.
