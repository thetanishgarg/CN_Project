Key idea: DNS only finds the address. A separate TCP connection then goes to that address, TLS secures it, and HTTP runs inside. The client only ever knows the edge's IP. The backends are hidden behind nginx.

Before the demo

Arrive 15 minutes early. Everyone on the same hotspot.

  1. Every Mac: git pull, then ipconfig getifaddr en0. If any IP differs from config.env, Mac 1 fixes it, pushes, and everyone pulls again.
  2. Every Mac: ./demo.sh ready (Mac 1 and Mac 4 one after the other). It starts that Mac's services, resets to the clean start (firewall off, DNS normal, standby edge up) and runs that Mac's tests.
  3. Mac 4: ./demo.sh capture for a fresh Wireshark capture on today's IPs.
  4. Every Mac: ./demo.sh check. Everything should be OK.
  5. Every Mac: open a second tab with ./demo.sh logs and leave it visible (DNS queries / nginx requests / backend logs scroll live).
The one rule that bites: nginx and dnsmasq read config.env only when they start. If an IP changes, run ./demo.sh ready again on Mac 2, Mac 1 and Mac 4.

DNS

  • dnsmasq answers app and api.team1.test with the edge IP, TTL 30.
  • Unknown *.test names: NXDOMAIN (we're authoritative: local=/team1.test/).
  • Everything else (google.com) is forwarded to 8.8.8.8, so clients keep internet.
  • Why .test: reserved for testing. .local is mDNS/Bonjour on macOS and never reaches our server.
  • dig asks the server directly. curl and Safari go through mDNSResponder, which caches.

TCP

  • 3-way handshake: SYN, SYN-ACK, ACK. Sequence numbers start at a random ISN.
  • Reliability: every byte numbered; receiver ACKs; missing data retransmitted on timeout or duplicate ACKs.
  • Flow control: the receive window (Win=) stops the sender overrunning the receiver.
  • Socket pair = (client IP, ephemeral port, server IP, server port).
  • Refused = host up, no listener, RST. Timeout = no reply at all (host down or firewall drop).

TLS

  • Terminated at nginx (Mac 2). Backends need no certificates.
  • Trust: cert signed by Team1 Local CA. The CA is in each client's Keychain, plus a bundle for macOS curl via ~/.curlrc (macOS curl ignores the Keychain).
  • Cert: RSA 2048, SHA-256, SAN app + api, serverAuth, 365 days (Apple rejects more than 825).
  • ECDHE gives forward secrecy: the session key is never sent and can't be recovered later from the server key.
  • SNI is plain text in ClientHello, so the hostname is visible even with HTTPS.

HTTP and caching

  • Endpoints: /, /api/status (no-store), /api/cache (max-age=60 + ETag). Header X-Backend: A|B.
  • HTTP/2 negotiated by ALPN in the TLS handshake: binary, multiplexed streams, header compression. HTTP/3 = QUIC over UDP (explain only).
  • Fresh hit (no request), conditional (If-None-Match → 304, no body), full (200 + body).
  • /api/status is no-store so caching can't hide the load balancing.

Phase 2 extensions

A · Backup DNS

Mac 4 runs the same dns/start-dns.sh, so the records are identical. Clients list Mac 1, then Mac 4. Stop Mac 1: names still resolve and dig shows SERVER = Mac 4.

DNS failure = names stop resolving. App failure = names resolve, but the service is down.

B · TTL and record change

TTL 30. Change the record: dig (which asks the server) sees it immediately, but the macOS cache returns the old IP until 30 s pass. A flush (dscacheutil -flushcache; killall -HUP mDNSResponder) switches at once.

Production: lower the TTL days before a migration, because the old long TTL is already cached everywhere.

C · Service isolation (pf)

macOS pf rules in anchor com.apple/team1-backend: allow TCP to the backend port only from Mac 2 and the standby edge (Mac 3), drop everything else silently. Stateful (keep state), so replies are allowed. remove restores the original state.

Like a security group that only allows the ALB's group: defence in depth, and the edge is the only way in.

D · HA failover

max_fails=1 fail_timeout=10s marks a failed backend down for 10 s. proxy_next_upstream error timeout http_502 http_503 retries the request on the other backend. proxy_connect_timeout 2s.

Passive health check (learns from real requests). nginx Plus and AWS ALB also do active probes. Remaining SPOF: the edge.

E · Edge cutover

Standby nginx on Mac 3 with the same generated config and the same certificate (the key moved by AirDrop, never git). X-Edge shows which edge answered. Point DNS at Mac 3: cached clients keep hitting Mac 2 for up to 30 s, new lookups go to Mac 3, and nothing fails because both edges serve.

Faster: floating IP with VRRP/keepalived (about 1 s, same L2), or a managed multi-AZ load balancer.

F · Injected fault

Diagnose bottom-up along the request. Partial credit for method, so say each step out loud. ./troubleshoot/diagnose.sh stops at the first failing layer.

Cross-questions

Say your answer out loud, then open it. Quiz each other in random order.

DNS

What's the difference between DNS resolution and the HTTPS connection?

DNS is a lookup: a UDP question to port 53 returns an IP. Then the client opens a separate TCP connection to that IP on 443 and runs TLS and HTTP over it. DNS can succeed while the connection fails (wrong record, nginx down), and you can connect by IP with no DNS at all.

Why does DNS use UDP?

One small question, one small answer. No handshake, so it's faster, and the client simply retries if a packet is lost. TCP 53 is used for large answers and zone transfers.

Why .test and not .local?

.test is reserved for testing (RFC 2606/6761). On macOS, .local is handled by mDNS/Bonjour multicast on port 5353, so the query would never reach our DNS server.

Why can dig and curl give different answers?

dig sends its own packet straight to the DNS server. curl and Safari call the OS resolver (mDNSResponder), which caches answers for the TTL. After a record change, dig sees the new IP immediately while curl uses the cached one until the TTL expires or you flush.

What happens to google.com if a client uses Mac 1 as DNS?

dnsmasq isn't authoritative for it, so it forwards the query to 8.8.8.8 and relays the answer. The client keeps normal internet.

What is TTL, and why 30 seconds?

How long resolvers and clients may cache an answer. 30 s makes record changes (failover, cutover) visible quickly, at the cost of more queries. In production you lower the TTL before a migration.

TCP and ports

Walk me through the three-way handshake.

SYN carries the client's random initial sequence number. SYN-ACK carries the server's own ISN and acknowledges client ISN + 1. The final ACK acknowledges server ISN + 1. Both sides now agree on sequence numbers and data can flow. Wireshark shows relative numbers starting at 0.

What is an ephemeral port? Show me one.

A temporary high port (49152–65535) the OS picks for the client side, e.g. 64537 → 443 in our capture. The server listens on a fixed well-known port: 53, 443, 3001, 3002.

How does TCP make delivery reliable?

Every byte has a sequence number. The receiver acknowledges what it got. Missing segments are retransmitted after a timeout or duplicate ACKs. The receive window does flow control, and congestion control adapts the sending rate to the network.

"Connection refused" vs "timed out"?

Refused: the host is up but nothing listens on that port, so its kernel answers SYN with RST (wrong-port demo, stopped backend). Timeout: no reply at all, because the host is down or a firewall silently drops the packet (our pf rules use block drop).

TLS and certificates

Why does the browser trust our certificate?

The edge certificate is signed by our private CA (Team1 Local CA), and we installed that CA certificate as trusted on every client. The client also checks that the name is in the SAN (app.team1.test), that the cert is within its dates, and that the server has the matching private key (it signs the key exchange).

What does TLS termination mean here?

nginx on Mac 2 decrypts HTTPS. From nginx to the backends it's plain HTTP on the private LAN. Certificates live in one place, backends stay simple, and the edge can read headers to route and load-balance.

Why can't Wireshark show the HTTP request?

It travels inside TLS Application Data records, encrypted with session keys only the two endpoints know. That's the point of HTTPS. We read headers at the endpoint with curl -v.

Why is the certificate visible in one connection but not another?

TLS 1.2 sends the Certificate message in plain text. TLS 1.3 encrypts everything after ServerHello, including the certificate. The capture forces one TLS 1.2 request so we can show it. Browsers use 1.3.

Can someone on the Wi-Fi see which site you visit over HTTPS?

Yes, partly: the DNS query is plain UDP, and the SNI field in ClientHello is plain text (app.team1.test). They can't see the path, headers or body.

Why not just use curl -k?

-k turns off certificate validation, so it proves nothing and would accept an impostor. The PDF forbids it. Our curl validates against a trust store that includes our CA.

HTTP, caching and load balancing

Fresh hit vs conditional request vs full request?

Fresh: within max-age=60 the client uses its copy without asking. Conditional: after that it sends If-None-Match with the ETag; if unchanged, the server answers 304 with headers only. Full: no cached copy, so 200 with the whole body.

Why does the 304 work through the load balancer?

/api/cache returns an identical body on A and B, so the ETag (a hash of the body) is identical. Whichever backend gets the conditional request recognises the ETag.

Why doesn't the client need the backend IPs?

DNS points at the edge only, and nginx holds the backend pool. Backends can be added, removed or replaced without touching clients or DNS, and they're hidden from the outside.

Round-robin vs least_conn?

Round-robin takes turns: A, B, A, B. least_conn sends each request to the backend with the fewest active connections, which is better when requests vary a lot in length.

What exactly does 502 Bad Gateway mean?

The edge itself is fine (DNS, TCP and TLS all worked), but it got no valid response from any upstream backend. 504 is the timeout version.

HTTP/1.1 vs HTTP/2 vs HTTP/3?

1.1: text, one request at a time per connection. 2: binary, many multiplexed streams over one TCP connection, header compression, negotiated by ALPN in TLS. 3: runs on QUIC over UDP, which avoids TCP head-of-line blocking (explanation only).

Resilience (Phase 2)

How does nginx know a backend is down?

Passively. When a real request to it fails (refused or timeout), max_fails=1 marks it down for fail_timeout=10s and the request is retried on the other backend. After 10 s nginx tries it again with real traffic. Active health checks (probing /health) exist in nginx Plus and AWS ALB.

What's still a single point of failure, and how would you remove it?

The edge on Mac 2: DNS points at one IP. Remove it with a standby edge plus DNS change (our Ext E, slow because of TTL), a floating IP with VRRP/keepalived (about 1 s), or a managed load balancer spread across availability zones.

Why did some clients keep using the old edge after the cutover?

They had cached the old DNS answer and keep using it until its 30 s TTL expires. That's why the old edge must keep serving for at least one TTL after the switch (a drain), and why you lower the TTL before migrating.

Why does the firewall allow Mac 3 as well as Mac 2?

Mac 3 is the standby edge. During a cutover it must still reach both backends, including Backend B on Mac 4. Everyone else is dropped.

Why put pf rules in an anchor?

An anchor is a named sub-ruleset. Our rules live there without touching the main ruleset, so removing them is just flushing the anchor. macOS only evaluates anchors under com.apple/, so ours is com.apple/team1-backend.

What does ARP do in our setup?

Before the first IP packet to Mac 2, the client broadcasts "who has 10.128.139.225?" and learns Mac 2's MAC address, because frames on the LAN are delivered by MAC address. See it with arp -a.
